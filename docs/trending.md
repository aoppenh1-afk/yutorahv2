# Trending by upload cohort

The page offers 24 hours, week, month, year and all time. Week, month and year mean rolling 7, 30 and 365 days. It ranks lifetime YUTorah views among shiurim uploaded in that window. Dividing views by age would measure an average rate, and would not recover views earned during the selected period. Actual rolling view totals would need historical counter snapshots.

Upload time comes from `shiurdatesubmitted` or `shiurDateSubmitted`. Recording time remains a separate field. The [YUTorah search page](https://www.yutorah.org/search/) distinguishes date given from date uploaded, and its [search script](https://www.yutorah.org/js/search/main.js) uses the public `Search/GetSearchResults` endpoint with `sort_by` and `facet_query`. Upload-date filters use inclusive [Solr ranges](https://solr.apache.org/guide/solr/latest/query-guide/standard-query-parser.html). Timestamped values retain their UTC offsets. The legacy endpoint's unzoned values use Eastern time, consistent with paired mobile API responses. Some upstream dates have day precision, so the interface discloses that limitation for the 24-hour view.

Live research on October 2, 2026 found that the mobile API ignored view-sort query parameters. The website endpoint returned HTTP 500 for the requested view-count sorting, and later probes encountered Cloudflare challenges. The implementation therefore uses the site's ID ordering and ranks locally. It does not depend on a successful upstream view sort. When that endpoint is blocked or fails response validation, the service falls back to the mobile API. It ranks upload cohorts locally while scanning the API's public library. The two search endpoints expose slightly different public totals, so coverage refers to the source used for that scan.

The website source reads at most thirty matching records per request. The mobile fallback reads at most four pages, each with thirty records, because that API ignores upload filters. A compact server-only bitmap records unique IDs and cohort membership. Repeated pages cannot inflate coverage. Missing or failed pages leave the chart incomplete and are revisited on the next library pass. The latest page is refreshed during longer scans to update counters. Completion requires unique-ID coverage to match the source's library total. A shrinking total invalidates the scan. These are reads from a changing upstream library, rather than an atomic database snapshot. Dated website queries filter upload time and duration before retrieval, then order by descending ID. Subsequent requests add an upper ID bound. A fixed upload window prevents later uploads from shifting the scan's offsets. All time includes archival records with missing upload dates. Each pass checks the remaining count, strict ID ordering, view counters, date bounds and durations before advancing the cursor. The chart is complete only after all matching records have been scanned. Zero-view records count toward coverage but do not occupy the viewed chart. Downloads, upload date and ID break view ties.

While indexing, the page displays coverage and provisional rankings, then requests the next pass. A winner on a later page can replace an earlier result. The home preview also identifies incomplete coverage. Automatic indexing only runs on the trending page and refreshes that chart independently of follows, related learning and the homepage feed.

The existing search database stores twenty reserved `trending:v1:*` rows, one per period and duration combination. Each row contains at most thirty provisional winners, a scan cursor, a mobile coverage bitmap when needed and the last completed top thirty. A failed rebuild can therefore keep serving the completed chart. No archive-sized payload table, new credentials or schema migration is required. Ordinary search cleanup excludes these reserved rows. Mobile pages are shared across chart variants for sixty seconds, with at most thirty-six cached pages. In-process promises coalesce requests; database leases coordinate separate server instances and expire after sixty seconds. Incomplete passes are cached for three seconds. Completed day and week charts are cached for five minutes, month charts for thirty minutes, year charts for six hours and all-time charts for twelve hours. Source failure keeps a cached snapshot for at most 24 hours, retains its timestamp and bounds retries. Incomplete or stale responses bypass CDN caching.

Large cohorts require an initial scan, especially all time. The upload window's end is displayed separately from the last indexing update so a long scan does not silently move the meaning of “past week.” A cohort whose remaining count changes must restart, rather than claim complete coverage. Source access failures do not turn into successful empty charts.

Warm charts before opening the page, or schedule the same command from an existing job runner:

```sh
npm run trending:warm -- --url https://YOUR_SITE --period week
npm run trending:warm -- --url https://YOUR_SITE --period all --max-passes 20000
```

Omit `--period` to warm all five periods. Use `--minutes 10`, `20` or `30` to warm a duration variant. The command is rate limited, has a pass budget and resumes the persisted cursor after interruption. A cold all-time scan can take hours. When the website source is blocked, the mobile fallback also needs a full-library pass for shorter periods. The command fails visibly on an upstream error, rather than endlessly retrying a blocked endpoint.

Tests cover rolling boundaries, Eastern offsets, recorded versus uploaded dates, duration filtering before limiting, winners beyond the first page, incomplete source responses, duplicate and out-of-order IDs, changed cohorts, Cloudflare fallback, duplicate offset pages, persistent bitmap resumption, hidden internal cursors, leases, cache expiry and stale failure recovery.
