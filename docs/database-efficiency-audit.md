# Database efficiency audit, October 5, 2026

The largest remaining opportunities are avoiding duplicate metadata scans, reducing idle worker queries, and stopping unnecessary transcript republication. Compressing final transcript text is a lower priority. The current code already separates public transcript reads from the generation database when the D1 archive is configured.

This audit covers commit `1bc3147fd66e10ee967ec28703e8531fb9d7d67d`. It changes no application behavior or deployed database. Findings below distinguish source inspection, local reproductions, and historical measurements. Production environment variables, current usage, deployed revisions, query plans, and traffic were not inspected. Deployment descriptions come from the repository's [delivery record](transcript-delivery-research.md), which also records that there was no running transcription VM at that time. Worker findings therefore describe what happens when that worker is enabled, not measured current production traffic.

The graph available for this repository was generated October 2. Indexing this worktree failed because an incompatible active index generation blocked the index worker. Graph discovery, caller/callee traces, and coverage checks were followed by direct reads of the current search, transcript, archive, source, worker, and SQL paths. New archive files were outside that graph. This is a source-backed audit of those paths, not a claim of exhaustive graph coverage.

The current data paths are:

| Operation | Source and cache behavior |
| --- | --- |
| Metadata search | Upstream YUTorah pages, then query-specific candidates in Neon on Vercel or D1 on Cloudflare. Completed runs last one hour; unfinished runs can resume for 24 hours. |
| Title autocomplete | Permanent title/vocabulary index, bounded process cache, browser cache and 200 ms debounce. |
| Public transcript and spoken-word search | D1 archive when `TRANSCRIPT_ARCHIVE_URL` is set. Otherwise the configured PostgreSQL reader or HTTP service. Archive failures do not fall back to Neon. |
| Transcription and notes | PostgreSQL jobs, leases, checkpoints, completed transcripts and notes. A durable outbox publishes to D1. |
| Sources and source sheets | Read transcript content through the gateway, but cache transcript snapshots, extraction state, and Sefaria text in the separate search database. |
| Trending | Twenty reserved database records, bounded top-30 results, shared refresh leases and process caches. |
| Personal library and listening progress | Browser storage. These updates do not consume database reads or writes. |

Free tier has several separate limits. D1 currently allows 5 million rows read and 100,000 rows written daily across the account, 500 MB per database, and 5 GB total storage. Index maintenance adds writes; a result limit does not cap rows scanned. D1 has no egress charge. Workers Free separately allows 100,000 requests daily and 10 ms CPU per invocation. A hit inside the Worker's Cache API saves D1 queries but still invokes the Worker. [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [Worker limits](https://developers.cloudflare.com/workers/platform/limits/).

Neon's current published Free allowance is 100 CU-hours and 5 GB public network transfer per project monthly, with 1 GB storage per project. Repository measurements from October 2 recorded an actual `512MB` enforced limit. Check the existing project's enforced capacity before a migration; the newer advertised allowance does not establish this project's current limit. Frequent queries also prevent its five-minute idle suspension. At a hypothetical constant 0.25 CU, 30 days online consumes 180 CU-hours. That is a sizing illustration, not measured usage. [Neon plans](https://neon.com/docs/introduction/plans), [storage announcement](https://neon.com/blog/neon-free-plan-1-gb-per-project), [compute lifecycle](https://github.com/neondatabase/website/blob/main/content/docs/introduction/compute-lifecycle.md).

1. **Identical cold metadata searches can create independent scans.** In [completeSearch](../lib/complete-search.ts), the fingerprint lookup and run insertion are separate, and the [schema](../db/search-postgres/001_search.sql) has a nonunique fingerprint index. Leases coordinate an existing run, but do not coordinate its creation. In a local SQLite fixture, two concurrent calls for the same query created two run IDs, fetched eight upstream pages and stored 240 hits. One initial pass would fetch four pages and store 120 hits. Both used the real search implementation.

   Atomically claim a fingerprint before fetching its first page. Other requests should join that run. Use a short database transaction to claim ownership, then fetch outside the transaction. Keep a generation/run identifier so old clients cannot resume a replacement scan. Process-local promise sharing is useful, but cannot replace coordination across Vercel instances. Verify concurrent creation, expiry, failure recovery and changed upstream totals.

2. **Broad searches do work proportional to the complete candidate set, even when only 30 results are shown.** [completeSearch](../lib/complete-search.ts) downloads four 30-item pages per pass, stores full JSON plus searchable text, then recounts accumulated hits. [The client](../app/torah-app.tsx) starts the next pass after 400 ms and continues automatically. It does not pause that loop when the document becomes hidden. A visitor who wants the first page can therefore initiate an entire archive scan.

   For a 22,770-candidate example, a clean full scan needs 759 upstream pages and 190 passes. Counting all accumulated candidates after every pass logically visits 2,177,370 candidate rows before allowing for sorts, filters or duplicate viewers. This is arithmetic from the code, not measured D1 billing or PostgreSQL I/O. Maintain committed progress incrementally and perform the completeness audit at completion. Pause hidden-tab polling and return a suggested retry delay to clients waiting for another lease holder. A separate fast, provisional result path could improve first results, but exact global sorting and filtering still require complete coverage. Do not silently truncate candidates or label provisional counts as exact.

3. **Idle worker loops can keep Neon active continuously.** Each lane in [runWorker](../apps/worker/src/worker.ts) sends a leadership query, checks notes work and checks transcription work. Each claim includes an expired-job update and a claim query. [OperatorRuntime](../apps/worker/src/operator-runtime.ts) uses a one-second idle delay; the CLI path uses five seconds. `enqueueMissing` shares concurrent work only while its promise is pending, so [NotesStore](../packages/transcription/src/notes-store.ts) repeatedly attempts the version insert and scans active transcripts for missing notes. Five idle lanes mean five leadership checks and ten claim statements per queue type per iteration, plus the shared notes-enqueue transaction. Query latency lengthens the actual iteration.

   Use one idle coordinator with backoff and jitter, waking local lanes immediately on an operator change or new job. Queue notes transactionally when a transcript completes; keep an occasional reconciliation scan for recovery and existing transcripts. Move expired-lease recovery onto a bounded schedule. Preserve active-job heartbeats and leadership safety. Reducing idle delay to 30 seconds still prevents Neon from sleeping; a true idle mode needs all background database activity to stop or back off past the suspension interval.

4. **The publisher also polls while transcription is paused.** [CLI startup](../apps/worker/src/cli.ts) launches `runPublisher` alongside `serve-operator`, independently of the worker's start/stop control. [runPublisher](../packages/transcription/src/publication.ts) checks its outbox every 30 seconds, approximately 2,880 empty reads per day before query time. An open operator page adds four snapshot queries every 10 seconds while active or every 60 seconds while paused. Hidden operator tabs already stop polling.

   Drain pending publications promptly, then back off empty polls or wake the publisher from local completion events, retaining periodic durable reconciliation. Distinguish lightweight runtime status from the 100-job snapshot. Share snapshots briefly across operator tabs and load job history only when needed. Coordinate this with the worker and catalog loops; optimizing just one loop will not restore database idle suspension.

5. **Re-importing unchanged metadata republishes an unchanged transcript.** [TranscriptionStore.enqueue](../packages/transcription/src/store.ts) unconditionally updates title, teacher and media URL on conflict. The [publication trigger](../db/transcription/007_publication.sql) fires on those updated columns without checking whether their values changed. [publishPending](../packages/transcription/src/publication.ts) then reads the full public transcript before the archive can compare content. A disposable PostgreSQL reproduction marked a transcript published, enqueued the exact same catalog record again, and observed a newer pending generation followed by one full transcript read and publication attempt.

   Add null-safe value-change predicates to the upsert and trigger, including the active pointer. Only changes to the active public transcript should queue publication; corrections to inactive history should not export the current transcript again. Preserve the existing guarantee that corrections arriving during an upload remain pending. Test equal values, actual edits, null media URLs, pointer changes and old transcript corrections.

6. **Notes status changes retain complete transcript bodies.** [Archive publication](../packages/transcription/src/archive.ts) hashes a JSON document containing segments and notes status, and [D1ContentObjects](../packages/transcription/src/d1-content.ts) retains immutable chunks for every distinct hash. Publishing queued, cleaning, generating and completed notes in a fixture left four complete content versions for the same transcript. Search rows correctly stayed at three, so the existing `search_version` reuse already avoids repeated FTS indexing for those notes-only changes. The four-body outcome requires the publisher to observe all four states; rapid transitions can coalesce in the outbox.

   Keep transient notes status in the small status record. Publish immutable timed text and completed notes as separate versioned content, or publish combined bodies only when public text changes. Coalesce state transitions. Add a retention policy for abandoned staging data and deliberate historical versions. Existing versioned URLs advertise one-year immutable caching, so deleting those versions earlier would change the delivery contract. Do not apply a blanket deletion of every noncurrent object.

7. **Live archive publication lacks the importer's write budget and duplicates the initial spelling dictionary.** The [importer](../scripts/migrate-transcript-archive.ts) accounts for `rows_written`; [publicationTarget](../packages/transcription/src/publication.ts) does not pass those accounting hooks to its D1 adapter. For every new transcript, [publish](../packages/transcription/src/archive.ts) tries to insert each unique word and its deletion keys. It does not check whether the word is already represented in the packed base dictionary. A three-segment fixture containing only already-seeded vocabulary added 54 delta-key rows and executed 71 SQL statements during publication. Those statement counts are not Cloudflare's billed row-write counts.

   Maintain exact word membership for the base and delta dictionaries, and generate keys only for new words. Insert words/keys in bounded groups instead of one statement per key. Record real read/write metadata and impose a durable daily publishing budget with headroom for all databases, FTS/index maintenance, other processes and readers. Classify exhausted daily quotas separately from transient errors and defer until reset. The existing exponential retry eventually retries hourly; it does not reserve capacity. Compact the delta dictionary periodically within a measured migration budget.

8. **Search cache retention is time-based but not capacity-bounded.** [Run creation](../lib/complete-search.ts) deletes at most five expired runs when another run is created. A single live run can still contain a very large candidate set, and expiry alone does not delete anything when traffic stops. Each `search_hits` row contains the full normalized shiur payload and another searchable text representation. Overlapping queries repeat the same metadata in different runs, with a primary key and four additional sort indexes per row.

   Add bounded scheduled cleanup, explicit storage/row budgets, and admission limits for new broad scans. Protect active leases and resumable runs. Store reusable metadata once per content revision and keep compact per-run IDs, rank, position and match flags. A plain mutable shared metadata row could change a completed run's filters/order underneath it, so preserve snapshot semantics with revisions. Consider longer TTLs for popular completed runs only after storage is bounded. PostgreSQL DELETE makes space reusable but does not guarantee immediate filesystem shrinkage; avoid promising a capacity recovery without measuring it.

9. **Completed pages still repeat database work; every new run performs legacy title backfill.** A local completed-search page-two call issued three SQL statements: load the run, aggregate counts, and select the page. The API always returns `no-store`. The library sort uses position, with no matching `(run, position, id)` index; popularity parses views from JSON. The existing sort indexes help some orders, but large offsets and additional filters still need query-plan measurements. [seedCachedTitles](../lib/title-index.ts) also runs before each new expansion, grouping an anti-join over cached hits to find titles missing from the permanent catalog. `LIMIT 120` bounds returned rows, not necessarily work when none are missing.

   Cache completed response pages by run, normalized refinements, sort and page, with TTL no longer than the run's remaining lifetime. Cache refined counts and perform the completeness check once. Keep pending/mutating passes uncached. Move legacy backfill to the existing indexing command with a durable completion marker. Consider keyset pagination and replace or add sort indexes only after comparing latency against storage/write cost. Initial cache creation should also share concurrent identical work.

10. **Title learning runs again for candidates already in the catalog.** [indexTitleStatements](../lib/title-index.ts) constructs term arrays and spelling keys for every page. The unchanged-title predicate avoids rewriting catalog rows, but key generation, transport, database parsing and conflict checks still occur. [The PostgreSQL adapter](../lib/search-postgres.ts) serializes these batches under a schema-wide advisory lock and executes their statements sequentially. All searches that learn titles can queue behind that lock.

    Derive spelling updates from only inserted or changed titles, and move learning off the response's critical path through durable, bounded work where practical. Keep the run's vocabulary snapshot stable. Use larger PostgreSQL-specific set-based batches where parameter limits permit, without changing D1 limits or crash recovery. Do not merely remove the lock; it currently prevents frequency-update deadlocks. Payloads sent into Neon are not the same metric as Neon's outbound-transfer allowance, although the work still adds latency and compute.

11. **Sources reintroduces transcript bodies into Neon.** [sourceSnapshot](../lib/sources-cache.ts) stores timed transcript text in `sources_runs` for 60 seconds. Every cold instance reading that snapshot transfers the body from the search database. After expiry, another visit fetches the transcript again and writes a fresh snapshot. [sourcesResponse](../lib/sources-handler.ts) obtains this snapshot before checking whether extraction is already complete or returning one cited source text. [advanceSources](../lib/sources.ts) also reconstructs/hashes the complete text before reading the cached result. Completed extraction expires after seven days. Thus a Sources visit can touch Neon even though basic transcript delivery is on D1.

    Use the archive's verified text revision to address completed source results directly. Retain complete extraction by text revision plus extractor version, checking the small active-version pointer when freshness is needed. Avoid using `transcriptId` alone because in-place corrections keep that ID. Keep raw text in the archive and fetch it only for extraction; retain only small results and progress in the search database. Cache successful public source responses, leaving pending work uncached. The [Sources poller](../app/sources-panel.tsx) can continue for 300 successful pending responses and lacks the transcript reader's hidden-tab pause; add that pause and server-directed backoff. Move automatic source warm-up after confirmed archive activation, since [the worker](../apps/worker/src/worker.ts) currently starts it after PostgreSQL completion while D1 publication happens separately.

12. **Smart transcript search makes one sequential spelling query per word occurrence.** [TranscriptArchive.search](../packages/transcription/src/archive.ts) awaits vocabulary lookup inside its word loop, followed by the FTS query. A fixture searching `quantum quantum quantum` made four SQL calls, including three identical spelling lookups. Sixteen qualifying words can mean 17 sequential statements. `LIMIT 20` in the final search does not establish that only 20 rows are scanned or ranked.

    Deduplicate normalized words first. Batch requested keys with word/slot identifiers into bounded queries, preserving a per-word candidate cap and D1's 100-parameter limit. Compare exact, Hebrew, alias, prefix, typo, common and no-match queries before changing FTS structure. Normalize equivalent request URLs so capitalization, spacing and parameter order do not fragment the 15-second search cache. Keep mode, aliases and limit in the key. Longer caching is possible if the product accepts delayed visibility or uses a publication revision; do not query that revision from D1 on every otherwise cached request.

13. **The existing versioned-content path is not used by the reader.** [TranscriptReader](../app/transcript-reader.tsx) requests the unversioned URL and fetches `fresh=true` after notes completion. It receives a version but does not use it for later content requests. [The gateway](../lib/transcript-gateway.ts) parses and reserializes archive JSON and discards the archive's ETag. [The Worker](../apps/transcript-archive/src/index.ts) already serves raw versioned JSON and skips the pointer lookup for a versioned read. A cold unversioned body uses two SQL calls, pointer plus chunks; a cold versioned body uses one. An edge-cache hit uses zero D1 queries. Chunk count determines body rows read.

    Preserve the initial one-request body load, then reuse returned versions for browser/session caching. When a small status response gives a new version, fetch that immutable URL rather than forcing a fresh unversioned body. Stream the successful gateway response with a controlled header allowlist instead of decoding and encoding it. Preserve ETags and add conditional handling before expensive body reads where it helps. Canonicalize allowed Worker query parameters. Manual fresh reads still need a bounded refresh policy. Cloudflare's Cache API is local to each data center and does not implement the stale directives used by the shared header; verify actual cache behavior rather than treating Vercel's stale behavior as an archive guarantee. [Cache API documentation](https://developers.cloudflare.com/workers/runtime-apis/cache/).

14. **Storage changes should focus on indexes and repeated derived data.** The [earlier storage investigation](search-storage-research.md) measured 220.05 MiB for title vocabulary, 128.57 MiB for catalog/title terms, and 60.04 MiB for spelling keys before the split. It measured only 4.17 MiB of raw final transcript text for 284 active transcripts. Those are historical measurements, not current sizes. Separate local experiments found 38.86 MiB saved by replacing the compact-phrase B-tree with a hash index, and 85.25 MiB by omitting catalog term arrays. Rebuilding the B-tree alone recovered 29.54 MiB, so most of the first saving was bloat recovery, not an inherent hash-index advantage. Newer autocomplete storage must also be included in today's budget.

    Re-measure before migrating. Preserve all phrase and spelling matches initially; rare one-off phrases can be important names. Deriving terms instead of storing them needs exact JavaScript/SQL normalization parity, and the previous experiment had one mismatch. In D1, check whether the explicit `(shiur_id, version)` segment index is redundant with the unique `(shiur_id, version, segment_index)` index. Benchmark the FTS prefix indexes and repeated adjacent-segment text before removing them. PostgreSQL still builds and retains its own transcript search fields/indexes despite public search moving to D1. Making those optional could save storage and generation work, but only after checking HTTP-reader, operator and recovery consumers. Published active data, unpublished later data in the blocked Neon project, and resumable checkpoints must remain intact.

15. **Smaller reads and operational measurements are still worthwhile.** [scanSelections](../apps/worker/src/selections.ts) repeatedly calls `targets()` and then selects one target in JavaScript, including once per candidate recording. Every call retrieves all targets and computes their imported counts. Replace these with targeted reads, retaining the existing locked budget check and checks for concurrent disable/filter changes. Plan retention for completed checkpoints, obsolete transcript versions and completed notes' cleanup inputs only after verified publication, backups and recovery requirements are satisfied. These are secondary to the active scan and polling costs.

    Add a shared-CDN TTL for [autocomplete responses](../app/api/suggestions/route.ts), whose current header only specifies `max-age`, and verify `x-vercel-cache` on the deployed runtime. The process cache is per instance; it is not a shared quota guard. [Vercel's cache headers](https://vercel.com/docs/caching/cache-control-headers) explain explicit CDN TTLs. Apply inexpensive request/concurrency controls before costly search creation and refresh work. Keep budget accounting out of per-read database writes. The [D1 adapter](../lib/d1-http.ts) already exposes read/write metadata hooks that can support aggregate telemetry without logging transcript text.

For a new transcript, the expected database work should be explicit:

| Stage | Current work | Reduction target |
| --- | --- | --- |
| During generation | Claim, state changes, checkpoint lookup/save, heartbeat about every 20 seconds, final atomic publication into PostgreSQL | Retain recovery and lease safeguards. Avoid empty multi-lane polling around these jobs. |
| Archive publication | Outbox lookup, one full PostgreSQL content read for each observed generation, D1 pointer reads, body write and verification read, segment/FTS/dictionary writes | Publish changed content once, then changed completed notes once. Make status updates small. No export for unchanged metadata. |
| Public initial body, cold archive cache | Two D1 statements for pointer and chunks | One on a known version; zero D1 statements on an existing edge-cache hit. No Neon read when the archive is selected. |
| Reader awaiting notes | Initial body, then up to ten status polls about 30 seconds apart, fewer when notes never appear; hidden tabs pause | Keep status small; fetch immutable new content only after a real version change. |
| Spoken-word search, cold cache | One spelling query per qualifying word occurrence plus one FTS statement in smart mode | Deduplicate/batch lookups and share cached results. |
| Optional source preparation | Separate search-database cache reads/writes and external Sefaria requests | Run after verified archive publication and reuse immutable extraction results. |

Validation performed for this audit:

- In-memory SQLite using the real metadata-search code reproduced duplicate cold runs and measured the three statements on a completed page request.
- In-memory SQLite using all archive migrations reproduced repeated spelling lookups, base/delta vocabulary duplication, and four content versions through the notes lifecycle.
- A disposable local PostgreSQL 17 cluster with all transcription migrations reproduced unchanged metadata queueing another full content export. This was not a production database or a performance benchmark of the deployed PostgreSQL version.
- Twelve existing archive, publication and read-cache tests passed, with no skips. This included the PostgreSQL outbox integration test. Tests were bundled from this checkout using the main checkout's installed build dependencies because this worktree has no `node_modules`.
- No live load test, production query execution, paid service, migration or deployment was performed. The local test server was stopped afterward.

Before implementing storage migrations, collect current table/index sizes, daily D1 reads/writes, Neon transfer and CU-hours, cache-hit ratios, and p50/p95 latency for a short fixed query corpus. Measure both cold and warm requests. Record statement counts separately from scanned rows and transferred bytes. A local query-count reduction is evidence of avoided work, not a percentage latency or billing guarantee.

The first implementation batch should address items 1, 3-5 and 9, alongside usage counters. Then budget archive publishing and remove duplicated Sources input. Use those measurements to choose the larger metadata-storage and index changes. These changes can retain the existing free services and search behavior; they do not require a paid cache or a database-provider migration.
