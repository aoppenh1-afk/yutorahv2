The database efficiency changes are implemented in this checkout. The public search and archive migrations were applied on October 5, 2026, and the archive Worker was deployed. Website deployment and verification are recorded in [PR #19](https://github.com/aoppenh1-afk/yutorahv2/pull/19). The transcription migration must run before the worker is restarted.

The original findings and baseline experiments are in [the audit](database-efficiency-audit.md). Its descriptions refer to the code before this implementation.

| Area | Implemented behavior |
| --- | --- |
| Duplicate metadata scans | A database creation lease coordinates hosts; a process also shares identical requests. The creator rechecks for an existing run after acquiring the lease. Expired leases recover after crashes. PostgreSQL document writes and cleanup share a transaction lock, including cleanup through the maintenance command, so an attaching search cannot lose its document. |
| Search progress and pages | The committed run records its candidate count. Completeness is checked once when scanning finishes. Filtered page rows carry their count through a window aggregate; empty pages use a count fallback. Completed responses have bounded process and HTTP caches. |
| Metadata storage | Hits reference content-hashed documents instead of repeating the complete JSON payload. Existing cached hits remain readable. New document payloads have a transactional 64 MiB ceiling; candidate reservations have a 50,000-hit ceiling across ordinary runs. Completed runs are evicted under capacity pressure. A broader request returns an explicit narrowing request; it never silently reports a partial result as complete. |
| Title learning | Already-known unchanged titles skip tokenization and spelling-key writes. PostgreSQL batches more titles per statement. Legacy hit backfill runs through the indexing command. The frequency lock remains for writes that change vocabulary. |
| Idle worker | Lanes share queue admission, use one statement per claim including exhausted-lease recovery, and back off from five seconds to ten minutes. Local durable writes wake them immediately. Notes discovery reconciles every fifteen minutes and is otherwise targeted inside transcript completion. |
| Publication | Unchanged metadata and edits to inactive transcripts do not create publications. Notes lifecycle changes update the small archive pointer; markdown/text changes publish content. Idle publication polling backs off to fifteen minutes. Source preparation runs after a successful archive publication. |
| Archive storage | New immutable manifests reference shared timed-text objects. Notes/metadata versions reuse timed text and FTS rows. Uploads check chunk metadata and send only missing chunks, including on interrupted retries. Legacy full JSON objects remain readable, including old version URLs. The redundant segment index is removed. Old published versions remain available. |
| Publication budget | Publisher and importer share a persistent, file-locked daily ledger: 60,000 conservative write units by default, including reservations for indexes/FTS and observed writes. Storage defaults to a 450 MiB ceiling. Budget exhaustion delays the outbox until the next UTC day before loading another full transcript. Partially staged segments and completed dictionary entries are reused on retry. These are application limits with headroom, not provider-wide accounting: other administrative writers must be included in operational usage checks. |
| Transcript search | Unique query words share one batched spelling lookup plus one FTS query. New words already present in the base/delta dictionary do not create duplicate delta keys. SQL batches respect D1's 100-parameter limit. |
| Delivery | Worker cache keys normalize query options and omit ignored parameters/fragments. Cache API entries use explicit supported TTLs. The gateway forwards JSON bytes and ETags; conditional requests are forwarded. Readers use published version URLs and a bounded cache. Database-only readers reject immutable-version requests rather than attaching an incorrect immutable guarantee. |
| Sources | Only trusted published status supplies the text version. Extraction fetches that immutable content version. Completed results are read before fetching the transcript or rebuilding its character map. Raw transcripts are no longer copied into search storage. Process input snapshots have entry/byte limits; completed state drops intermediate resolver data. Ready results last thirty days in SQL. Source-text/ready caches have bounded cleanup and a conservative 32 MiB capacity target. Hidden tabs pause search and Sources polling. |
| Operator and selections | Operator snapshots are shared for thirty seconds; visible polling is thirty seconds while running and two minutes while paused. Selection reads fetch one target, and imported counts are maintained transactionally by triggers. Catalog wakeups have their own channel so notes/jobs cannot cause repeated catalog scans. |
| Retention | The publisher automatically checks once daily, including while no new publication is due. Completed checkpoints and cleanup inputs older than seven days require an acknowledged active publication; intermediate notes also require retained final notes. Inputs without final notes remain and do not occupy cleanup batches. The seven-day automatic policy was confirmed by the owner. The maintenance command defaults to a dry run. Pruning inactive transcript versions additionally requires verified, synced gzip backups and a ninety-day age threshold. Final transcripts/notes and retryable checkpoints are preserved. |
| Optional storage reductions | Owner-run scripts provide a compact phrase hash index and reversible removal of PostgreSQL transcript search indexes/vectors after archive-only search is configured and every active publication is acknowledged. They are separate from automatic migrations. Derived title term arrays remain because the earlier SQL tokenizer experiment did not preserve every Unicode match; PostgreSQL can compress/outsource long arrays instead. No rare vocabulary or FTS prefix features were discarded. |

Apply the migrations in this order:

1. Stop the worker while its schema changes. Run its existing `migrate` command with the worker database owner so `db/transcription/008_efficiency.sql` adds the imported counter and publication change flag. Earlier migrations must already be applied. Already acknowledged generations retain that state; pending generations remain queued for full export.
2. With the search database owner, apply `db/search-postgres/003_efficiency.sql`. It preserves cached rows and mirrors the existing search-run privileges on the new cache tables. For SQLite/D1 search storage, apply `drizzle/0006_search_efficiency.sql` through the existing migrations command. The Vercel build also performs idempotent SQLite setup and validates the PostgreSQL schema; it does not attempt owner DDL on PostgreSQL.
3. Apply `db/transcript-archive/0005_efficiency.sql` using the existing archive migration configuration.
4. Deploy the archive Worker before the website and Node publisher. It reads both legacy objects and the new manifest format. An older Worker cannot read new manifests, so rollback must retain this manifest-capable reader.
5. Deploy the website and restart the Node worker/publisher. Keep publisher and importer under the same service user and budget file. `TRANSCRIPT_PUBLICATION_BUDGET_FILE` overrides the default `~/.local/state/yutorah/d1-DATABASE_ID-budget.json`; `TRANSCRIPT_PUBLICATION_WRITE_BUDGET` may lower the daily budget, and `TRANSCRIPT_PUBLICATION_STORAGE_BUDGET` may lower the storage ceiling. A crash during the short ledger update can leave a lock file: verify no writer is running before removing a stale lock. Do not delete/reset the daily ledger during a restart.

For maintenance, set `SEARCH_DATABASE_URL` and/or the transcript owner's `TRANSCRIPTION_DATABASE_URL`, then run `npm run data:maintain`. It reports eligible cleanup without writes. `npm run data:maintain -- --apply` cleans bounded batches of expired query caches, orphan documents, obsolete input caches, and acknowledged completed checkpoints/notes. Repeat if a large backlog remains. PostgreSQL can reuse freed pages; returning allocated disk space may require owner-managed vacuum/repacking during a maintenance window.

Inactive-version pruning is separate: `npm run data:maintain -- --apply --prune-inactive --backup-dir PRIVATE_DIRECTORY`. Every candidate is locked, backed up to a file with private permissions, synced, decompressed and verified before deletion. Published D1 version objects are not removed.

For the optional archive-only PostgreSQL storage change, configure the website's archive reader and set `TRANSCRIPT_ARCHIVE_ONLY_SEARCH=true` on the worker before running `npm run data:maintain -- --apply --archive-only-search` with `TRANSCRIPT_ARCHIVE_URL` present. The command refuses any unacknowledged active transcript. Restore with `db/transcription-options/restore_postgres_search.sql` before disabling that flag. Measure actual title index sizes before applying `db/search-postgres-options/compact_phrase_index.sql`; it replaces only the equality lookup index and retains every phrase.

Local regression results:

- Two cold callers through different database wrappers: one run, four upstream pages and 120 stored hits in the initial pass. The audit baseline was two runs, eight pages and 240 hits.
- Two overlapping complete searches: 362 hits referencing 181 document payloads. A repeated warmed completed page performs zero SQL reads and returns an independently usable response.
- `quantmu quantmu quantmu`: two SQL reads, including one shared spelling lookup; the audit baseline was four.
- Queued, cleaning and generating publications: zero full PostgreSQL transcript reads. Final markdown changes perform one full content read. The existing outbox retry/concurrent-correction test still passes.
- Notes states create no new content chunks. Final notes upload only the new manifest and reuse one timed-text object and the same three segment rows; old immutable versions remain readable. An interrupted chunk upload sends only the missing chunk on retry and reconstructs Unicode text exactly.
- A PostgreSQL search paused between document reuse and hit insertion blocks concurrent orphan cleanup. After the hit commits, cleanup retains its document and the result remains readable.
- Completed Sources requests perform one initial immutable transcript fetch, then reuse the stored result without another transcript read or a stored input copy.
- The daily budget persists across a new instance, serializes concurrent reservations, rolls over on the UTC date, and blocks further writes at its limits.
- The idle publisher removes eligible checkpoints and intermediate notes while keeping final notes, recent checkpoints, unpublished checkpoints and inputs without final notes. The maintenance CLI preserves active, recent and unpublished transcript versions. A mismatched existing backup prevents deletion; successful pruning verifies and syncs the backup, including its directory, before removing the inactive database version. Run this integration test with `TEST_DATABASE_URL` pointed at a disposable PostgreSQL database and `npm run test:maintenance`.

Search, Sources, PostgreSQL queue/publication/recovery, read-cache, archive, worker quota scheduling, type checks, lint, and the website production build passed locally. The full worker run initially had macOS failures because its Linux tests hard-code `/usr/bin/ffmpeg` and require passwordless sudo for tunnel scripts. Temporary test bundles substituted the installed Homebrew FFmpeg paths; all 31 pipeline/audio tests then passed, including five-session concurrency, pause, leadership loss, quota handling and recovery. GitHub Actions subsequently passed the full worker suite on Linux, including the six tunnel tests. No production usage or latency reduction is claimed from these local fixtures.

Continuation verification on October 5, 2026 passed 48 focused tests with no skips, using an isolated local PostgreSQL schema for each database fixture. This covered the publication upgrade, concurrent document cleanup, budget persistence, missing-chunk retries, idle retention, backup verification and Sources caching. The search and learning suites, TypeScript checks, lint, worker build and website production build also passed.
