# Recovering stalled requests after host execution pauses

The October 16 investigation compared requests started within the same two-hour window. All 36 timed-out requests overlapped large clock/execution discontinuities, while none of 150 successful requests did. The association is strong, but does not establish whether the VM host, networking, or upstream connection lifecycle caused the lost stream. Saved timeout histories had incomplete or empty output, rather than complete responses missed by the client. Available memory also fell below the existing admission floor.

The minimized regression replays an observed 17-second execution gap and 137-second wall/monotonic discrepancy. Previously, affected requests could hold inference capacity for the remaining three-minute monotonic silence period, in addition to time lost outside that clock. A targeted recovery mode now applies only to sessions already present at a corroborated disruption: a tick gap of at least 30 seconds, or at least four seconds plus a forward wall/monotonic discrepancy of at least 30 seconds. A wall-clock correction alone does not qualify.

After a five-second catch-up grace, the monitor reads persisted history to establish a baseline. If output remains unchanged, recovery uses the earlier of the ordinary silence deadline and a 60-second post-disruption deadline. It performs another bounded history read before cancellation. New output after catch-up restores the ordinary deadline; complete responses are recovered through the existing identity, finish, cost and content checks. Cancellation still requires owned abort, confirmed idle and deletion before returning capacity. New sessions retain the ordinary deadline. Clock changes cannot extend an already elapsed ordinary silence deadline.

The adapter records body-free `runtime_discontinuity` and `resume_watchdog_timeout` observations, and monitor metrics count discontinuities and recovery cancellations. These distinguish targeted recovery from normal timeouts without exposing source material or credentials. Model, effort, full-source contract, retry policy, publication verification and the 3 GiB memory safeguard remain unchanged.

Regression tests reproduced the old capacity stall before the fix and cover queued catch-up, genuinely resumed output, new requests, ordinary deadline preservation, clock-only corrections, verified completed history and confirmed owned cleanup. Validation: 136 tests passed, one optional live-catalog test skipped; TypeScript, targeted lint and formatting checks passed. Private correlation and timeout evidence is retained under `STATE/upgrades/stall-investigation-*`.

This change bounds wasted capacity after a disruption. It cannot prevent host pauses or promise a sustained throughput increase; production observations must distinguish recovery behavior from the underlying host and provider variability.
