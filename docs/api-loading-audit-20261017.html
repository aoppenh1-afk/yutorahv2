Faster loading for shiurim, collections and searches

The changes target API work, payload size and repeated requests. Shared snapshots avoid rebuilding cached collections on each server instance. Playable recording details arrive before optional metadata.

Initial directory: 667 KB → 293 KB decoded JSON.

Teacher identities, portraits and topic hierarchy remain available. Browse descriptions load when their section is opened.

Actual public catalog payloads measured locally. A warmed local collection took 20 ms, its next page 12 ms, and a neighbor response 9 ms. These individual local samples are not production latency forecasts. The previous production collection request took 12.7–15.3 seconds before caching.

Cache limits and recovery
  • Durable snapshots have a 16 MiB encoded compressed-data budget, at most 256 versions and 24-hour retention. Admission prunes old data under a database transaction lock.
  • Freshness windows are one minute for Home, five minutes for profiles, ten minutes for Daf and recording core, fifteen minutes for collections and thirty minutes for directories.
  • A last successful snapshot can serve during refresh; errors and unavailable responses do not replace it. Cache storage outages fall back to upstream reads and bounded memory storage.
  • Database leases coalesce work across hosts and reject expired or replaced writers. Browser retries honor bounded Retry-After responses. Missing pagination versions offer a fresh restart.
  • Browser storage is limited to 64 public response entries and 4 MiB. Public data caching is separate from private library synchronization.
  • New or unwarmed content can still need a slow first upstream read. Complete broad search rankings still require a verified archive scan. A permanent authoritative metadata mirror remains a separate storage and freshness project.
